# 0.1.1 著者別要約の試作・確認結果

仕様：[ARTICLE_AUTHOR_SUMMARIES_SPEC_0.1.1.md](../spec/ARTICLE_AUTHOR_SUMMARIES_SPEC_0.1.1.md)

## 試し方

1. 0.1.1の読込用フォルダへ更新する。公開済み0.1.0のZIPは変更していない。
2. 同じ著者の記事を2件以上、新しく要約する。0.1.0の過去回答は自動登録しないので、履歴の記事タイトルから再要約してもよい。
3. いずれかの記事タイトルから「この記事の感想」を選ぶ。対象以外の同著者記事の保存済み要約が参考情報として送られる。
4. 自由入力で話を続ける。感想の区間では同じ参考情報も送る。
5. 記事タブの「新しい会話」で、本文・会話・要約Mapがまとめて消える。

## 自動検証

475件成功。正常完了した要約だけの保存、再要約での上書き、IDによる著者の分離、タイトルの自然順、対象自身の除外、感想とその区間だけへの付与、本文の非混入、生成中の再取り込みでの旧要約登録防止、再起動後の復元、初期化と接続先変更時の削除、JSON非混入、保存失敗時の巻き戻し、送信・保存容量超過を確認した。

## Chromeの実ブラウザ検証

一時プロファイルで実際のIndexedDB・WebCrypto・画面を使用。2記事を要約してキャッシュ2件を作成し、第2話の感想に第1話の要約だけが付くこと、対象自身の要約と他記事本文が送信されないこと、再読み込みでの保持、新しい会話で本文・履歴・要約Mapがすべて空になることを確認した。この試験のOllama応答は模擬した。

## 実LLM検証

ローカルgemma3:12bへ架空の短い記事を送信。アプリの同じ背景コントローラを通して要約保存と感想用メッセージを作成し、生成したメッセージを実OllamaのAPIへ送った。GUIから実Ollamaへの通し試験を行ったという意味ではない。

- 同じ著者の小説「灯台の記録 第1話」
- 同じ著者の無関係な随筆「休日のスープ」
- 対象記事「灯台の記録 第2話」

3件を個別に要約し、第2話の感想には第1話と随筆の要約2件を参考情報として付けた。第2話自身の要約と他記事本文は除外した。実際の回答は以下のとおり。

> 「灯台の記録 第2話」を読ませていただきました。
> 
> このお話は、ミナが父を探すという葛藤と、灯台という不気味な空間描写が印象的でした。特に、止まった時計が一列に並び、針が同じ時刻を指しているという描写は、時間が止まっているような不穏な空気感を醸し出していて、ミナの置かれている状況の切迫感を表しているように感じました。
> 
> また、「青いレンズに父の影が映ったが、ミナはレンズに手を伸ばさず、その前で立ち止まる」というシーンは、ミナが父への想いと、手紙の警告の間で揺れ動く心情を象徴しているように思われ、読後感が深く残ります。
> 
> 前回の第1話では、父の失踪と灯台への導きが描かれていましたが、今回の第2話では、ミナの行動原理や、灯台に隠された秘密への予感を感じさせる展開で、続きが非常に気になります。

今回の回答は第1話との関係に触れ、料理記事は混ぜなかった。短い架空記事1組での確認であり、任意の作品での正確性や関連判定を保証するものではない。

## 制限・未確認

- 要約もモデルが生成した参考データであり、誤りや省略がある。
- 同じ著者でも別作品が混ざる。明示的な作品選択・シリーズ管理・連作専用タブはない。
- 全件を送る方針のため、件数と長さが増えるとモデルのコンテキストやアプリの送信上限に達する。暗黙の間引きはしない。
- 記事DB全体8MiB、履歴2MiBを維持する。要約Mapの保存にも容量を使い、容量超過はエラーになる。
- 要約Mapは既存のstateメタデータに保持するため、Mapが大きくなった場合の書き込み最適化はしていない。
- 0.1.0の過去要約からの自動移行は行わない。
- Firefox・Edgeでの新機能の実操作、大量記事、実容量超過、保存途中のプロセス強制終了は未確認。
- この試作は未公開。コミット・タグ・GitHub Release・ストア申請は行っていない。

両ブラウザの試作用ZIPは各29ファイルで、展開先・ソースとのバイト一致を確認した。SHA-256は `dist/verification-0.1.1.json` に記録し、0.1.0の検証記録・配布物は保持している。
