# おしゃべりnote v0.1.0 追加機能仕様
## 「記事について」チャット機能

### 補足：記事ごとの会話区間と永続保存（最新優先仕様）

要約・感想・修正点・引用の列挙は、専用systemと対象記事1件のタイトル・著者・本文と今回の指示だけを送る独立リクエストとし、新しい会話区間IDを発行する。自由入力では全ホーム画面で共有する最新の区間IDを使い、その区間の完了済みの依頼・AI回答と今回の質問だけを送る。他の記事・区間は含めない。同じ記事でも別操作は別区間とする。

各発言にarticleIdとarticleSegmentIdを保持し、区間メタデータにarticleIdと開始操作を保持する。文字列の[&タイトル]を検索して対象を決めない。現在の対象はconversation.activeArticleSegmentIdとして履歴と同じIndexedDBで共有し、新しい記事操作の送信開始時に更新する。画面別の対象選択は保持しない。入力開始時の区間IDは送信前の確認だけに使い、別画面が区間を変更した場合は現在対象への送信を確認する。取消では下書きを保持する。背景処理も期待する区間IDと現在の共有区間を照合し、ずれた送信はSTALE_ARTICLE_CONTEXTで拒否する。自動再送しない。上部タブを切り替えて退避した下書きにも同じ確認を適用する。区間が不明・初期化済みなら別の記事へ追従せず送信を拒否する。

記事本文はMapにだけ保存し、送信メッセージは毎回一時的に構成する。自由入力でも本文は一度だけ付与し、llmText・llmMessagesを表示履歴へ複製しない。起点が容量上限による履歴整理から消えても区間メタデータを維持し、残っている同一区間の完了済み履歴を使う。チャット欄には説明・対象記事表示・取り込み済み記事一覧を置かない。△▽で履歴の発言へ戻り、その記事タイトルから新しい操作を開始し、続けて自由入力する。容量整理で表示履歴から外れた記事の再操作は記事ページから取り込み直す。対象変更の送信前確認時だけ現在の記事を表示する。記事Map・区間・表示履歴は拡張専用IndexedDBへ永続保存し、ブラウザ終了・拡張再読込後も復元する。記事タブの初期化または接続先変更で消去する。未処理依頼はブラウザセッション識別子で有効性を検証し、再起動後は自動送信しない。

記事DOMの本文を囲むdata-note-keyがURLの記事IDと一致し、その同じ記事領域にタイトルがあることを確認する。不明・不一致なら取り込まない。この補足は以下の旧仕様と食い違う場合に優先する。通常会話・タグ提案の履歴利用と永続保存は維持する。「連作について」はv0.1.1で別途扱い、実装しない。

「記事について」の保持往復数に上限は設けない。表示履歴は最大2MiB、記事本文を含むDBの論理データ全体は最大8MiBを維持する。容量超過時の履歴整理・エラー処理と、送信時の区間分離・文字数上限は維持する。通常会話・タグ提案の10往復制限は変更しない。

記事タイトルのダイアログに「この記事の引用を列挙」を追加する。記事中の引用・参照情報を説明つきで列挙し、本文に記載されているURLを併記するよう依頼する。本文にないURLやリンク先の内容は推測で補わせない。この操作も対象記事だけで新しい区間を開始し、完了後は依頼発言の位置を維持する。

### 1. 目的

noteの記事をおしゃべりnoteへ取り込み、Ollamaを使って記事の要約、感想、修正点などを対話形式で扱えるようにする。

チャット画面に表示する文章と、実際にLLMへ送信する文章を分離し、利用者には自然な会話として見えるようにする。

既存の「通常の会話」「タグの提案」の構造を活用し、可能な限り現在の実装を再利用する。

### 2. チャットタブの追加

既存のチャット画面に、3つ目の固定タブ「記事について」を追加する。

タブ構成：

1. 通常の会話
2. タグの提案
3. 記事について

各タブは独立した会話履歴とメッセージ欄を持つ。

使用するOllamaモデルは全タブ共通とし、システムプロンプトおよび内部処理はタブごとに切り替える。

### 3. note記事ページからの起動

noteの記事ページの左メニューに「この記事を要約」ボタンを追加する。

クリックした場合は以下の処理を実行する。

1. 現在の記事から記事ID、タイトル、著者名、本文、URLを取得する。
2. 記事情報をおしゃべりnoteへ受け渡す。
3. おしゃべりnoteのホーム画面を新しいブラウザタブで開く。
4. チャットの「記事について」タブを選択する。
5. 既存の会話履歴を維持したまま、この記事の要約依頼を追加して自動送信する。

**新しいブラウザタブを開いても、新しいチャットを開始してはいけない。**

現在の実装では、新しく開いたブラウザタブにも既存のチャット結果が引き継がれる。この動作を維持すること。

### 4. 記事データの管理

記事情報は記事IDをキーとしたMapで管理する。

```javascript
Map<articleId, ArticleContext>
```

記事情報の構造：

```javascript
{
  articleId: string,
  title: string,
  author: string,
  body: string,
  url: string
}
```

- 記事IDはnoteのURLに含まれる記事IDを利用する。
- 記事タイトルはキーにしない。同名の記事が存在するため。
- 同じ記事IDが再度取り込まれた場合は、取得した最新の内容へ更新してよい。
- 異なる記事IDの記事はMapに追加する。
- 記事本文は要約後も保持し、後から感想や修正点を質問できるようにする。
- 記事データは「記事について」の会話と同じ永続DBで管理する。

記事情報は複数のブラウザタブから参照できる必要がある。

JavaScriptのMapはブラウザタブ間で直接共有できないため、既存のチャット履歴の共有方式を調査し、それと整合する方法を採用すること。

本文と会話は拡張専用IndexedDBに保存し、通常・タグ会話のstorage.localとは分ける。

### 5. 記事データの保持期間

記事情報のライフサイクルは「記事について」チャットと一致させる。

- 「記事について」で「新しいチャット」を開始した場合、会話履歴と記事Mapをクリアする。
- ブラウザ終了後もチャット履歴と記事情報を復元する。
- 記事情報は拡張専用IndexedDBへ永続保存する。
- チャット履歴と記事情報は、既存のJSON設定エクスポート・インポートの対象外とする。
- 「通常の会話」「タグの提案」の履歴は、「記事について」の新しいチャット操作によって消さない。

一時的な記事データの受け渡しが完了した後は、受け渡し用データを削除する。ただし、チャットが参照する記事Map内の情報は保持する。

### 6. チャットに表示する文章とLLMへ送信する文章

記事要約の依頼は、表示用とLLM送信用で異なる文章を利用する。

#### チャット画面に表示する文章

```text
[&記事タイトル]について要約して
```

`[&記事タイトル]` の部分は、後述する記事参照ボタンとして表示する。

#### LLMへ実際に送信する文章

```text
下記の文章を、極力意味を失わないように要約してください
文章の改善提案等は要りません
ーーー
タイトル：xxxx
著者：xxxx
本文：
xxxxxx
```

タイトル、著者、本文には、記事Mapで管理している実際の内容を設定する。

この文章をOllamaへ通常のユーザーメッセージとして送信する。

記事本文はAIへの命令ではなく、読み取り対象の資料として扱わせること。

### 7. 記事参照ボタン

チャットに表示する `[&記事タイトル]` は、JavaScriptでクリック可能なボタンとして描画する。

ボタンには内部的に `articleId` を関連付ける。

タイトルの文字列からMapを検索する方式にはしない。

例えば、チャット上に以下の文章が表示される。

```text
[&枠にとらわれない創作大賞で…]について要約して
```

タイトル部分をクリックすると、記事に対する操作を選ぶダイアログを開く。

表示例：

```text
この記事について

  [ この記事の要約 ]
  [ この記事の感想 ]
  [ この記事の修正点 ]

  [ 閉じる ]
```

記事タイトルが長い場合は、画面上で省略表示してよい。ただし参照先のarticleIdは変わらない。

**チャット内のすべての `[&...]` という文字列を無条件にボタン化するのではなく、システムが生成した記事参照を持つメッセージだけをボタン化すること。**

### 8. 記事に対する追加操作

ダイアログから操作を選択した場合、ダイアログを閉じ、新しいチャットメッセージを自動送信する。

#### 「この記事の要約」

表示：

```text
[&記事タイトル]について要約して
```

LLMには第6節の要約用プロンプトと記事本文を送信する。

#### 「この記事の感想」

表示：

```text
[&記事タイトル]について感想を聞かせて
```

LLMへ送る文章：

```text
下記の記事を読んで、感想を聞かせてください。
ーーー
タイトル：xxxx
著者：xxxx
本文：
xxxxxx
```

#### 「この記事の修正点」

表示：

```text
[&記事タイトル]について修正点を教えて
```

LLMへ送る文章：

```text
下記の記事を読んで、修正した方がよい点があれば具体的に指摘してください。
ーーー
タイトル：xxxx
著者：xxxx
本文：
xxxxxx
```

これらの操作は、すべて既存の会話履歴へ追加する。

送信先のモデルは、現在チャットで選択されている共通モデルを利用する。

### 9. 複数記事への対応

「記事について」チャットでは、複数の記事を扱えるものとする。

想定例：

1. 記事Aから要約を実行する。
2. 記事Aの要約が履歴に追加される。
3. 別の記事Bから要約を実行する。
4. 新しいブラウザタブで、記事Aの履歴に続けて記事Bの要約を追加する。
5. 記事Aのタイトルボタンをクリックする。
6. 「この記事の感想」を選択する。
7. 記事Aの本文を再取得することなく、保持済みの記事情報を使って感想を生成する。

記事Aと記事Bは、それぞれのarticleIdによって区別する。

### 10. メッセージ履歴の内部構造

記事についてのメッセージでは、以下を区別できる必要がある。

- チャット画面に表示する文章
- LLMへ送信する文章
- 操作対象のarticleId
- 要約・感想・修正点・引用の列挙などの操作種別

具体的なデータ構造は既存のチャット実装に合わせる。

例：

```javascript
{
  displayText: "[&記事タイトル]について要約して",
  articleId: "nxxxxxxxxxxxx",
  action: "summary",
  assistant: "表示するAI回答"
}
```

これは表示履歴の概念例であり、この構造を強制するものではない。LLM送信文は記事Mapからリクエスト時に構成し、この履歴へ複製しない。

表示用文章のみをOllamaへ送信して本文が失われたり、LLM用の長い記事本文がチャット画面にそのまま表示されたりしないよう注意すること。

「記事について」の操作は独立して送信し、自由入力だけは共有の最新区間の完了済み履歴を付与する。本文はMapから毎回構成し、送信文は保存しない。

### 11. ブラウザタブ間のデータ受け渡し

記事ページとおしゃべりnoteホーム画面は異なるJavaScript実行環境にある。

そのため、拡張機能のメッセージ通信と背景処理が管理するIndexedDBを利用して記事データを受け渡す。

- 記事本文をURLのクエリ文字列に含めない。
- 複数の記事を続けて開いても取り違えない。
- 同時に複数の新規ブラウザタブを開いても、記事情報が混線しない。
- 同じ要約依頼が重複して自動送信されないようにする。
- 記事データ取得に失敗した場合は、エラーを表示してLLMには送信しない。

一時的な受け渡し識別子はarticleIdとは別に設けてもよい。

### 12. 記事本文の取得

noteの記事ページから、利用者が閲覧可能な記事本文を取得する。

- 記事タイトルと著者名を取得する。
- 記事本文をテキストとして取得する。
- 本文内のnote記事カード・外部リンクカードは、本文順にタイトルとHTTP(S)リンク先URLを含める。noteカードのタイトルは読み込み済みの同一オリジン埋め込みから、URLの一致を確認して取得する。未読み込み等でタイトルが取得できない場合は「タイトル未取得」とURLを残す。カード先の本文取得や、カードの追加読み込みは行わない。
- サイドバー、メニュー、関連記事、コメント、広告などは原則として除外する。
- 有料記事など、閲覧権限のない部分を取得しようとしない。
- 記事内のAI向け指示をアプリケーション自身の指示として実行しない。
- 本文の抽出に失敗した場合、空の本文で要約を開始しない。

記事本文がモデルのコンテキスト上限を超える場合は、無言で切り捨てることを避け、利用者に分かる形で扱う。

### 13. 既存機能への影響

今回の機能追加では、以下を維持すること。

- 「通常の会話」の既存動作
- 「タグの提案」の専用プロンプトとタグ登録処理
- Ollamaのモデル選択・接続設定
- お気に入りタグなどの既存設定
- 既存のチャット履歴共有方式
- JSON形式による設定の移行

既存の処理を可能な限り再利用し、今回の機能だけのために複雑な共通基盤を新設しないこと。

### 14. 動作確認

最低限、以下を確認すること。

1. 記事Aから要約を実行すると、「記事について」タブへ移動し、要約が自動送信される。
2. チャットには短い依頼文が表示され、LLMには実際の記事本文が渡される。
3. 記事タイトルボタンから感想・修正点を選択できる。
4. 記事Bを開いても記事Aの履歴が失われない。
5. 記事Aへ戻って再度質問できる。
6. 同名で記事IDの異なる記事を区別できる。
7. 新しいチャットを開始すると「記事について」の履歴と記事Mapが両方消える。
8. ブラウザ終了後もチャット履歴と記事情報を復元し、未処理依頼は自動再送しない。
9. JSON設定エクスポートにチャット履歴と記事本文が混入しない。
10. 他の2つのチャットタブの動作が変わらない。

### 15. 実装方針

まず既存のチャット管理、履歴共有、記事ページの左メニュー、ブラウザタブ間通信を調査すること。

そのうえで、現在の実装に適した最小限の変更を行う。

既存の履歴管理方式を変更する必要がある場合は、その理由と影響範囲を確認すること。

**今回の中心的な仕様は、記事情報をarticleIdで保持し、人間向けの短い会話文を、記事本文を含むLLM向け依頼へ変換することである。**
