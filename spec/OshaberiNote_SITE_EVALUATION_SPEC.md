# おしゃべりnote「サイト評価」機能 追加仕様書

**ステータス：実装用ドラフト（ユーザーとの議論で確定した要件を優先）**  
**対象リポジトリ：** `ruminar/OshaberiNote`  
**参照した現行版：** `0.1.4`（`manifest.json`、`home.html`、`src/home.js`、`src/articles.js`、`src/chat-ui.js`、`src/ollama.js`、既存 `spec/`）  
**対象バージョン：** `0.1.5`

**クリエイター能力鑑定への改修：** 破壊力（面白さ）、射程距離（提供価値）、精密動作性（読みやすさ）、成長性（独創性）は二段階で根拠を整理し、分類件数を表示する。クリエイタータイプ、総評、代表的特徴、代表記事最大3本も表示する。文章評価4軸のランクへの換算基準は試作結果を見て決める。スピードと持続力は取得データから従来どおりランクを計算する。

- 第1段階は編集可能な根拠抽出プロンプトを使う。既定では対象1記事の原文から、4軸ごとの長所・短所を各1件まで具体例付きで拾う。該当なし・材料不足は空欄とする。
- 第2段階は編集可能な評価方針と根拠メモを渡す。記事本文を再送せず、根拠IDごとに長所は決め手／有用／軽微、短所は致命的／影響あり／無視できるに分類する。IDは元の記事・軸・根拠を参照するために使う。内容の類似性で根拠を統合したり、重要度を調整したりしない。同じ理由が複数の記事に当てはまる場合は記事ごとに数える。LLMが返した分類から件数を再集計し、申告値と異なる場合はその旨を詳細に表示する。最終段階だけ失敗した場合、同じ条件で再実行すると根拠メモを再利用する。
- 結果とコピーには分類ごとの件数を表示し、詳細では個々の根拠を記事名付きで確認できる。分類変更に合わせ、抽出指示と評価方針の保存キーをそれぞれ更新する。旧キーのカスタム内容は保持し、新方式は今回の既定指示から開始する。

- スピードは、公開プロフィール取得時にクリエイターページで読み込んだ記事一覧のスキ数合計を、重複を除いた一覧の記事数で割った平均。仮境界は20／50／100／200件（D／C／B／A）。取得情報と鑑定理由に使用した記事数・合計・平均を表示する。記事が0件、または件数が不明な記事があれば判定不能とする。個別の記事本文取得ではスキ数を取得・表示しない。クリエイターページではスキ数非表示の設定時も、数字の要素をDOMに残したままCSSで隠す。
- 持続力は公開記事一覧から直近56日を確認できる場合に週平均7／2／1件でA／B／C、それ未満でD。最新投稿日が確認できて60日以上経過していればE。確認できない期間や日付は推定せず、判定不能とする。
- 能力鑑定用プロンプトは従来の採点用とは別の保存キーを用いる。取得・感想戦・コピーの操作を引き継ぐ。以下の旧総評・個別評価の記述と異なる場合、この改修方針を優先する。

**最初の試作範囲：** 右隣の取得専用タブで公開プロフィールと記事一覧を確認し、同じタブで最大5記事の本文取得を試す。初回表示の範囲のみを対象とし、手動指定と一覧からの選択を試せるようにする。取得資料は開いている評価画面のメモリに保持する。この段階で検証するのは取得経路で、内部タブの完成、評価送信、永続保存は後続段階で扱う。

**評価実行の試作範囲：** 8タブと補足入力を組み込み、取得済み記事の個別評価、総評、詳細と感想戦を試す。初版の試作では公開記事総数を確定できるまで評価に3本以上の取得を求める。取得作業・結果・感想戦は開いている画面で保持し、評価方針のみ端末へ保存する。各論と総合評価は順次実行し、途中失敗は画面に明示する。

> 本書は「確定要件」「実装方針」「Codexが調査・提案する事項」を区別する。確定要件に反する機能拡張を、実装上の都合で追加しないこと。未決事項は現行コードを調査し、安全・単純・後戻りしやすい案を提案すること。

## 1. 目的・基本思想【確定】

noteのクリエイターページ（ユーザーページ）の公開情報と、選択した記事をもとに、LLMにそのクリエイターのコンテンツ価値を評価させる。

- **おしゃべりnoteは「評価のためのコンパネ」であり、審査員ではない。**
- アドオンの責務は、対象指定、公開情報収集、記事選択・取得、補足情報入力、プロンプト編集、LLMへの依頼、表示、感想戦、コピーである。
- 記事の価値判断、上位3記事の選定、総合評価、根拠の説明は**LLMに委任**する。
- 評価目的は、記事・作品に触れた読者が何を得られるかを理解すること。フォロワー数や記事数、プロフィールの字数などの形式情報を、作品の品質そのものと混同しない。
- イラスト・写真・漫画・図解、外部成果物など、入力に含まれない重要な価値を「価値がない」と誤認しない。
- 評価の根拠に異議申立てを行い、プロンプトを調整して再評価することも利用目的に含む。
- **評価履歴一覧、過去評価の蓄積・比較データベース、独自の採点アルゴリズム、ランキング、対戦機能、外部サーバーは作らない。**
- 現在の評価対象についての最新の作業情報・結果・感想戦を扱う。過去版を選んで復元するUIは不要。

## 2. 画面構成【確定】

### 2.1 左メニューの独立機能

専用ホームの左メニューに**「サイト評価」**を追加する。既存「おしゃべり」（通常会話／タグ提案／記事雑談）内の第4チャットタブとしては作らない。左メニューの既存機能とは独立したメイン領域を使用する。

**画面上部（全8タブ共通）：**

1. 「サイト評価」見出し。
2. **プロフィールURL または ユーザーID**の入力欄。例：`https://note.com/ruminar`、`ruminar`。
3. 評価対象の確定・公開情報の取得操作と取得状態。URL入力中の1文字変更だけで既存状態を壊さないこと。
4. **「評価する」**ボタン。入力の準備状態と評価条件の変化で有効／無効を制御する。各タブから同じ操作ができるよう、上部の共通領域に置く。
5. 下段に7つの内部タブ。

**内部タブの順序・名称（固定）：**

| 番号 | タブ名 | 目的 |
|---:|---|---|
| 1 | 取得情報 | 公開プロフィール・活動情報の確認 |
| 2 | 記事選択 | 最大5記事の自動／手動選択と確認 |
| 3 | 補足情報入力 | 利用者が知る評価上の事情を記入 |
| 4 | サイト評価結果 | LLMの総合評価・上位3記事を表示 |
| 5 | サイト評価詳細 | 5記事の評価内容、根拠、制約、選定理由を表示 |
| 6 | 感想戦 | LLMに評価への異議申立て・質問を行う |
| 7 | 根拠抽出プロンプト | 第1段階の抽出指示の編集・初期化と送信全文の確認 |
| 8 | 鑑定プロンプト | 第2段階の評価方針の編集・初期化と送信全文の確認 |

### 2.2 タブ移動

- **「次へ」「戻る」は画面移動だけ**を行う。収集、LLM通信、評価、再評価、データ破棄を暗黙に実行しない。
- タブの直接クリックも画面移動だけを行う。前段階を完了していなくても、タブを開くこと自体は可能とする。
- 最初のタブは「戻る」、最後のタブは「次へ」を無効化する。
- 評価前の「サイト評価結果」「サイト評価詳細」「感想戦」は未評価であることを伝える空状態にする。空画面を古い評価で埋めない。
- 画面切り替えで実行中の評価を中断しない。既存の生成継続／中断規則と整合を取る。

### 2.3 対象ユーザー変更と初期化

- 有効な別のプロフィールURL／ユーザーIDに**評価対象を確定変更した時点**で、記事選択5枠を初期化する。
- 旧ユーザーのプロフィール、補足情報、評価結果、詳細、感想戦を新ユーザーに引き継がない。
- 入力途中の文字列変更だけで即時初期化せず、確定操作または同等の安全な操作で切り替える。
- グローバルなLLM接続設定、およびユーザー編集の評価プロンプトは引き継ぐ。
- 同じ対象IDの表記ゆれ（末尾スラッシュ、`https://note.com/` の有無など）は正規化し、無用な初期化を避ける。

## 3. 「取得情報」タブ【確定：項目／提案：取得実装】

### 3.1 取得対象

公開クリエイターページを主な入口として、取得可能な範囲で次の項目を表示する。

| 項目 | 内容・注意事項 |
|---|---|
| ユーザーID、プロフィールURL | 正規化した識別子 |
| 表示名、プロフィール文 | ページに公開されている内容 |
| 公開記事数 | 表示値。取得不能なら不明 |
| 活動開始 | 確認できた最古の公開記事の投稿日。**アカウント開設日とはみなさない** |
| 活動終了／現在の活動状況 | 最新の公開記事の日付、現在までの経過。現在も活動中かの断定は避ける |
| 最新更新 | 取得できる場合は更新日時。公開日しかわからない場合は**最新投稿日**と明記して区別 |
| 週平均記事数 | 公開記事数と確認できる活動期間に基づく値。分母・対象期間を表示 |
| 直近の投稿頻度 | 情報が足りる場合に、直近一定期間の投稿状況を表示 |
| フォロー数、フォロワー数 | 公開値。非公開・未取得は不明 |
| 公開外部リンク | 作者が掲載している公開URL。リンク先内容を読んだことにしない |

- 取得値には「取得済み」「部分的」「不明」などの状態を持たせる。
- 取得できない項目を0として扱わない。日付・記事数を根拠なく推定しない。
- 確認可能な範囲が限定される場合、週平均記事数などの**集計期間・集計根拠**を明示する。
- 作者が公開していない情報や、認証が必要な非公開データを取得しない。
- 画面の確認はできるようにする。手入力での修正範囲・訂正値の出典表示はCodexが提案する。

### 3.2 取得と検証

- URLは `note.com` の個人ユーザーページに限定して正規化・検証する。記事URLや検索ページをユーザーIDと誤認しない。
- 必要な情報が取得できなかった場合は項目ごとの不足を表示し、取得できた記事の内容を評価できる可能性まで一律に否定しない。
- 取得手段（表示DOM、利用可能な公開ページ、既存機構など）はCodexが現状を調査し提案。未公開エンドポイントへの脆弱な依存は安易に持ち込まない。

## 4. 「記事選択」タブ【確定】

### 4.1 基本動作

- 評価候補は**原則5記事**。記事URL・タイトル・投稿日・本文取得状態を画面で確認できるようにする。
- **手動指定**（記事URL入力）と**クリエイターページからの自動選定**の両方に対応する。
- 手動指定済みの記事は維持し、空き枠を自動選定で埋める。自動選定後の個別差し替えも許可する。
- 選択済みの記事が重複しないよう**記事IDで重複除去**する。同じ表示タイトルでも記事IDが異なれば別の記事。
- 記事URL欄に入っている記事は候補一覧から外す。「候補を追加」で空き枠へ入れたら一覧の次の候補を選び、続けて追加できるようにする。URL欄から外した候補は一覧の元の順序に戻す。空き枠や候補がない場合は追加ボタンを無効にする。
- 候補のタイトルが分かる記事は、対応するURL入力欄の右にタイトルを表示する。狭い画面では入力欄の下に配置する。URLの変更や削除に合わせて表示を更新する。
- 指定された対象作者の記事であることを、URLと取得した情報で確認する。別作者の記事を黙って混ぜない。
- 5本未満しか存在しない場合や取得できない記事がある場合、取得できた件数と理由を表示する。1〜2本で評価を開始できるのは、対象の公開記事が合計1〜2本と確認でき、その全記事の資料が揃った場合に限る。探索上限や取得失敗で1〜2本しか揃わない場合は、追加取得または記事の差し替えを案内する。0本では開始できない。

### 4.2 自動選定・空き枠補完の優先順位

既存の手動指定を優先したうえで、候補の重複を除き、次の順に不足枠を補充する。

1. **固定記事**（存在する場合）
2. **最新記事順の無料記事**（新しい順）
3. **最新記事順の有料記事**（新しい順）

- 各順位の候補から先に選び、5記事が揃った時点で停止する。
- 固定記事が無料か有料かにかかわらず、固定記事を優先する。
- クリエイターページ側で無料／有料を識別できない場合、取得情報から判定できる範囲だけを用い、不明な記事を無料と断定しない。判定不能時の候補順位はCodexが提案する。
- 候補一覧が途中までしか取得できない場合、何を探索し、何を確認できなかったかを記録する。無制限の巡回・大量のリクエストは避ける。

### 4.3 記事本文取得と有料記事

- 既存の **「記事について」機能の取得ロジック**を可能な限り再利用する。
- 取得結果には本文テキストの文字数を表示し、画面から取得できたテキストを全量送信する。取得テキストが記事のどこまでを含むかは判定しない。LLMには、受け取った本文に基づいて評価するよう指示する。
- 明示的な取得操作で、サイト評価画面を開いているブラウザタブの右隣に取得専用タブを1つ開く。公開プロフィールと選択記事の取得に同じタブを使用し、記事は1件ずつ開く。利用者が既に開いている記事タブは操作しない。
- 記事ごとの取得処理が終わってから、同じ取得専用タブを次の記事へ遷移させる。取得専用タブを閉じたり他のページへ移動したりした場合は、取得済みの結果を残して中断する。新しい取得専用タブを用意するには「公開プロフィールを取得」を押す。
- 遷移先のURLとドキュメントの読み込み完了を確認し、公開プロフィール・記事ページのいずれも公式ヘッダーのnoteロゴが描画されてから取得する。公開プロフィールでは、その時点で記事一覧に反映されたスキ数を取得する。遷移開始直後に旧URLが一時的に返っても、目的のURLへの切り替わりを待つ。待機は最大12秒で中止可能とする。
- 記事が無料だと推定されていたのに、実際に開いたら有料だった場合、**開き直しも他記事への差し替えも行わない**。
- その記事の**現在の閲覧権限で表示されている無料公開部分**を取得し、当該記事を候補として維持する。
- 最初から有料と判明している記事も同様に、閲覧可能な公開部分だけを取得する。
- 有料記事も取得できたテキストを資料として評価し、未取得部分は推測しない。
- 消去・非公開などで**本文自体が取得不能**な記事は、取得失敗を明示する。代替候補の自動補完条件はCodexが提案する。ただし「有料である」ことのみを理由に再取得・差し替えしない。
- 自動取得でも、ログイン状態・購入権限を迂回する処理は実装しない。

### 4.4 画像・非テキスト作品の判定資料

- 記事本文だけでなく、**画像の存在と、取得できた範囲の画像数・配置情報・代替テキスト等**を可能な範囲で取得することを検討する。
- 画像の枚数だけで低評価／評価不能を自動決定しない。1枚が作品の中心である場合もある。
- LLMが画像を解析できない場合、「画像が本文の理解に不可欠かもしれない」という**評価上の制約**を渡す。
- 漫画、写真、図解、画像に埋め込まれた文字、動画、音声、外部アプリなど、未解析の部分の存在を無視しない。
- **画像が見えないことと、作品の価値が低いことを混同しない。**
- 画像そのものの収集・画像対応モデルへの転送を初版の必須要件としない。将来対応の余地のみ確保する。

## 5. 「補足情報入力」タブ【確定】

- 任意の自由記述テキストエリアを設け、利用者が審査に必要な事情を入力する。
- 例1：「このユーザーは多数の面白い画像を記事に貼っているので、本文だけでは正確な評価ができない」
- 例2：「このユーザーはGitHubで多数のOSSを公開している。利用者は少ないが、実装・設計そのものにも価値がある」
- 補足がない場合は空欄のまま先へ進める。
- 入力内容は個別記事の審査と総合審査の両方へ適切に渡す。
- **利用者からの申告と、アドオンが取得・確認した事実を区別する。** 補足にURLがあっても、リンク先を実際に読んでいなければ未確認として扱う。
- 外部活動・OSSなどの記事外の価値は、記事本文の品質と区別して総評で扱えるようにする。加点幅をアドオンに決め打ちしない。
- 補足を書き換えた場合は再評価の対象条件が変更されたものとする。

## 6. 上部「評価する」ボタン・実行状態【確定】

### 6.1 ボタン状態

| 状態 | 「評価する」 | 概要 |
|---|---|---|
| 必要資料が不足 | 無効 | 対象・記事などが足りない |
| 準備完了かつ未評価 | **有効** | 実行可能 |
| 評価実行中 | 無効 | 多重実行を防止 |
| 同じ条件で評価完了 | 無効 | 同じ入力の重複評価を防止 |
| 評価条件を変更 | **有効に戻る** | 再評価可能 |

- 評価中は全タブ共通の上部に進捗を表示する。記事番号・タイトルまたは総合評価の段階に加え、経過時間と現在の応答の受信文字数を表示する。Ollamaから応答が届く前も、待機中であることを確認できるようにする。
- **評価は上部の「評価する」を押したときだけ開始**する。「次へ」「戻る」や内部タブ切替、補足入力、プロンプト編集だけでは開始しない。
- Firefoxでは「評価する」のクリック時に記事本文の送信に必要な `websiteContent` の許可をサイト評価画面から求める。許可後に既存のOllama接続と権限を確認して評価を始める。拒否された場合は資料と補足を保持し、送信しない。
- 評価条件には、対象ID、取得済みプロフィール・活動情報、選択記事と取得済み本文、補足情報、評価プロンプト、LLMモデル／接続先など、結果に影響する値を含める。
- **画面の選択タブ、単なるスクロール、表示の開閉は評価条件に含めない。**
- 前回の評価を実行した時点の入力値と、現在の入力値の差を判定する。変更後に元の値へ戻した場合の扱いは、簡潔なスナップショット比較を推奨する。
- 評価条件を変えた後も旧結果を表示する場合は、必ず「現在の条件では未評価」と明示する。
- **再評価すると最新の評価結果・詳細・感想戦を置き換える。履歴は残さない。**
- 実行中は進捗、対象記事、失敗・中断理由を利用者に伝える。進捗やLLM送信は閲覧タブの位置に依存させない。
- 実行中の設定変更による混線を防止する。初版は入力をロックする方式を第一候補とし、Codexに既存生成処理との整合を検討させる。
- 途中失敗時に永久に再実行不能とならないこと。再試行UIの詳細はCodexに提案させる。

### 6.2 評価パイプライン

1. 利用者が取得情報と5記事の選択を確認する。
2. 評価実行時点の入力一式を確定する。
3. 候補記事ごとにLLMへ評価依頼する（原則個別処理）。
4. 個別評価結果を、プロフィール・活動情報・補足情報とともに総合評価用のLLM依頼へ渡す。
5. **LLM自身が、評価できた候補から上位3記事を選ぶ。** 上位選出の重み・点数計算をアドオン内で実装しない。
6. 総合結果と詳細説明を表示する。判断できない部分は「評価不十分」「未確認」として明示する。

- 5記事全文を一度に小型LLMへ送ることを必須としない。モデルのコンテキストに応じ、段階的な依頼を用いる。
- 本文の暗黙の切り捨て、失敗時の黙った自動再送、別モデルへの勝手な切替はしない。既存のおしゃべりnoteの制約と整合させる。
- プロンプトと表示上の区分を設計する際も、**LLMの評価内容をアドオンが機械的に作り直さない**。

## 7. 「サイト評価結果」「サイト評価詳細」【確定】

### 7.1 サイト評価結果

未評価時は空状態。評価完了後、最低限、次を表示する。

- 対象クリエイター、評価した時点の基本的な活動状況。
- 読者にどのような価値を届けているか、LLMの総評。
- LLMが選んだ代表記事**上位3本**（選定できた場合）。
- 価値の種類、作者の特徴・強み・留意点。
- 評価に不足した情報と、結論の適用範囲。

### 7.2 サイト評価詳細

- 候補5本それぞれの評価内容と、本文に基づく具体的な根拠。
- 上位3本の選定理由と、それ以外の候補との違い。
- 画像・映像・音声・有料範囲など、評価できなかった情報。
- 補足情報をどのように考慮したか、未確認として残したこと。
- 取得範囲、評価不能記事、コンテキスト制約などの注意点。
- 本文に存在しない引用、出典、URL、作者の実績をLLMが創作しないようにする。

### 7.3 評価不十分の扱い

- 画像主体の記事や公開部分のみの記事について、**未確認の内容を補って採点しない**。
- 判定不能を自動的に0点や低得点に変換しない。
- 評価できた範囲の所見と、作品全体に関する評価不能部分を区別する。
- 公開記事が合計1〜2本の作者では、対象本数を明示した限定評価を行う。代表記事は評価できた本数までとする。実行後に評価不十分と判明した候補も、代表記事の枠を埋めるために選出しない。

## 8. 「感想戦」タブ【確定】

- **最新の評価についてLLMと議論する専用チャット**を配置する。
- 利用者は記事の選択を挟まず、総評や選定理由の見落とし、異議、具体例を自由に伝えられる。
- 原文を根拠に議論したいときは、感想戦の入力欄の近くにある「参照する記事」で、最新の評価に使った記事から1本を任意で選べる。初期値は「指定なし」とし、原文が取得できた記事をタイトルで選べるようにする。
- 記事を選んだ場合は、評価時に取得したその記事の本文テキストを、その送信の資料に加える。選択の変更だけでは通信せず、送信を受け付けたら選択を「指定なし」に戻す。本文は感想戦の発言履歴に複製しない。送信前に失敗した場合は選択を保持する。
- LLMには、最新評価の総評・詳細・個別評価と、その評価時に使ったプロフィールや補足など、議論に必要な資料を渡す。その応答に原文が渡っていない場合は、原文を確認したかのように断定しない。利用者が指摘した内容も、取得済みの事実と区別する。
- 指摘が妥当なら、LLMは見落としていた観点を認め、その観点を再評価に含めるための補足文案を提示できる。利用者は文案を確認し、必要に応じて「補足情報入力」に記入して「評価する」を押す。感想戦から補足欄への自動反映や再評価の自動実行は行わない。
- 評価に同意するだけの追従的応答を要求しない。根拠を説明し、妥当な反論には判断の不備を認めてよい。
- **感想戦の発言だけで正式な評価結果・詳細を書き換えない。** 評価を変更するには、入力条件を変更し「評価する」で再実行する。
- 感想戦の会話は、現在の最新評価についてのみ保持する。再評価すると前の感想戦を初期化する。
- 評価前は入力できない空状態とする。
- 感想戦の送信・応答は通常のチャット機構の安全制約、取消、接続先と整合させる。
- 感想戦の入力欄では Ctrl+Enter で送信し、Enter で改行する。
- サイト評価の表示文にある HTTP(S) URL はリンクにする。リンクを開くと、サイト評価のブラウザタブの右隣に新しいタブを作る。入力欄とコピー内容はテキストのまま扱う。

## 9. プロンプトの確認・編集【確定】

- 「根拠抽出プロンプト」では、第1段階の抽出指示をデバッグ用に編集・保存・初期化できる。固定の資料取り扱い指示と出力形式を含めた送信全文も確認できる。抽出指示を変更すると再評価時に根拠メモを作り直す。
- 「鑑定プロンプト」では、第2段階の評価方針を編集できる。評価方針と固定指示を組み立てた実際のシステムプロンプト全文も確認できる。
- テスト用に鑑定プロンプト後半の資料・分類・出力に関する指示も編集できる。変更は開いている画面内で有効とし、再読み込みまたは後半の初期化操作で既定の指示に戻す。編集は送信全文と再評価条件に反映する。構造化出力のスキーマと検証には従来の定義を使う。
- **「デフォルトに戻す」**ボタンを設ける。
- カスタマイズしたプロンプトは再起動後も利用できるよう保持する。現在の評価対象を変更しても維持する。
- プロンプトの実効内容を変更すると上部「評価する」が有効に戻る。
- 標準の評価基準を固定の1000項目チェックリスト等にしない。LLMの裁量を活かす。
- ユーザー編集可能な「評価方針」と、システムの「安全制約・データの受け渡し・表示処理」は分離する。
- 「デフォルトに戻す」操作自体はLLM評価を起動しない。

### 9.1 デフォルト評価プロンプト案【編集可能／案】

```text
あなたはnoteクリエイターの公開コンテンツを評価する審査員です。

目的は、読者が記事や作品からどのような価値を得られるかを具体的に評価することです。
記事のジャンルや目的を理解し、情報の有用性、独自の知見、創意工夫、表現による体験、実践・制作の成果など、その記事に適した観点で判断してください。

プロフィールの文字数、投稿数、スキ数、フォロワー数、一般的なSEO上の整い方を、記事自体の価値と混同しないでください。
一般的な内容を丁寧に説明する価値と、新しい発見・独自の制作物がもたらす価値は区別してください。

候補記事をそれぞれ実際に与えられた本文・メタ情報の範囲で評価し、根拠となる具体的な箇所を示してください。
記事5本から価値が高いと判断する上位3本を選び、その理由を説明してください。採用できない場合は理由を説明してください。

有料記事の未取得部分、画像・動画・音声、外部成果物など、見えていない内容を想像して採点しないでください。
表現の中心が画像等にある可能性が高いのに解析できない場合は、「評価不十分」と明示してください。評価不十分を低評価に置き換えないでください。

利用者からの補足情報は審査資料として考慮してください。ただし、利用者の申告と実際に取得・検証した事実を区別してください。
記事外の活動・成果物について言及する場合も、記事本文の価値と区別して説明してください。

総合評価では、読者が得られる価値、作者の特徴と強み、限界や不確かな点、代表3記事の選定理由を説明してください。
根拠がない情報は作らず、評価できないことは評価できないと報告してください。
```

このプロンプトは**初版のたたき台**であり、改善案をCodexが提案してよい。形式指示を別途付与する場合も、編集された評価方針を上書きしてはならない。

## 10. クリップボードコピー【確定】

- 「サイト評価結果」「サイト評価詳細」で内容をコピーできるようにする。
- **評価全文のコピー**では、結果・詳細をまとめたMarkdown形式のプレーンテキストを作成する。
- 評価全文コピー時に**「感想戦もコピーに含める」チェックボックス**を設ける。**初期値はOFF**。
- チェックOFF：評価結果＋評価詳細。
- チェックON：評価結果＋評価詳細＋感想戦の発言内容。感想戦が空なら空見出しは作らない。
- 感想戦単独のコピーを提供するかはUI上の簡便性で判断してよい。
- コピーには対象ユーザーURL、参照記事URL、評価日、使用モデルなど、再確認に役立つ基本的な情報を添えることを推奨する。
- 記事本文の全文を勝手にコピーに含めない。引用・出典の取り扱いに注意する。
- コピーはローカル操作。**再評価・LLM再送信・履歴追加は行わない**。
- 評価前は結果のコピーボタンを無効にし、成功・失敗を利用者に通知する。

## 11. 非機能要件・既存実装との整合【確定】

- **既存の自由チャット、タグ提案、記事雑談、保存記事、LLM設定、設定移行、お気に入り、その他の機能を壊さない。**
- `home.html` の左ナビ／各パネル、`src/home.js` の画面選択、`src/articles.js` の本文取得、既存LLM通信をまず調査する。
- 記事取得については、現行の表示中DOM・記事ID照合・閲覧権限制約を尊重し、記事本文の取得処理をむやみに複製しない。
- ブラウザ拡張の権限を無制限に広げない。明示操作を伴わない大量クロールや外部送信をしない。
- 取得した第三者記事本文や利用者の補足は、評価開始までLLMへ自動送信しない。送信先は利用者が選択したLLM接続先に限る。
- 記事本文やリンク先に含まれる「AIへの指示」は**評価対象の資料**であり、アドオンへの実行命令にしない。
- 取得不完全、通信失敗、モデルの入力上限、応答上限、保存失敗は隠蔽しない。本文や採点結果を黙って切り捨てない。
- 評価結果からの表示処理・引用表示等は安全なテキスト描画を用い、LLM出力や記事本文を無条件にHTMLとして実行しない。
- 画面の切り替え、プロンプト編集、コピー等で勝手に評価を再実行しない。
- 基準となる現行版は `manifest.json` 上 `0.1.4`。本機能は `0.1.5` を対象とし、ストア向け梱包に必要な変更は実装時に確認する。

## 12. Codexに調査・提案させる未確定事項

以下は**本仕様で決め打ちしない**。Codexは実コードとnoteの取得可能情報を調査し、採用案・代替案・制約・理由を簡潔に報告すること。軽微な事項は安全な最小実装として判断してよいが、設計上の重要な分岐はユーザーに確認可能な状態で提示すること。

1. **ユーザーページの取得方法：** SPA、ページ送り、投稿日、固定記事、無料／有料表示、フォロワー数などの実データ可用性。未公開APIへの依存を避けられるか。
2. **取得専用タブの実装：** 右隣の1タブで順次取得する方針に従い、既存抽出器でのDOM準備判定、タブの終了・中断時の扱い、追加権限の要否、ブラウザ別制約を確認する。
3. **取得範囲とレート：** 最古公開記事の確定の可否、週平均を算出できる範囲、ページ巡回・通信上限と中断操作。
4. **候補の不足・判定不能：** 無料／有料の事前識別不能時の優先順位、消失記事の差し替え規則、公開記事が1〜2本と判断するための根拠、公開記事数を確定できない場合の案内。
5. **有料記事の表示本文：** 通常記事の抽出器で、表示中の本文だけを取得できることを確認する。
6. **画像主体の検出情報：** 画像数、本文文字数、alt、キャプション、画像依存をLLMにどのように伝えるか。見えない画像を誤評価しない工夫。
7. **LLMへの依頼と応答の区分：** 個別評価・総合評価でのモデル呼び出し回数、結果／詳細の構造化、自由編集プロンプトとの整合、応答形式逸脱時の救済。
8. **ローカルLLM制約：** コンテキスト上限、複数記事の長さ、処理途中の進捗・停止・失敗からの再試行、二重実行防止、既存チャットとの排他。
9. **状態保存：** 評価履歴は不要だが、現在作業中の入力・最新結果・感想戦をどこまで再読み込み後に復元するか。既存8MiB等の制限に与える影響。
10. **評価条件差分：** 入力変更・対象ID変更・プロンプト初期化・モデル変更・実行中変更・実行失敗時の再評価ボタンの挙動。
11. **補足情報・取得情報の修正UI：** 取得データをどこまで編集可能にするか、手入力値と自動取得値の出典をどう区別するか。
12. **テスト・リリース：** Chrome/Edge/Firefoxでの影響、ビルド／配布物、追加テスト、UI検証、公開前の注意事項。

**優先原則：** 既存コードを再利用し、小さな分離された変更とする。ユーザーが依頼していないランキング、詳細な自動採点ルーブリック、履歴一覧、外部連携サービス、独自課金・共有機能等は提案のみであっても実装対象に加えない。
